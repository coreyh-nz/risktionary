# Risktionary

Risktionary is a multiplayer drawing game with AI-generated feedback. This monorepo contains both halves of the app:

| Directory                 | Description                                                  |
| ------------------------- | ------------------------------------------------------------ |
| [`backend/`](./backend)   | Spring Boot (Kotlin) API, WebSocket server                   |
| [`frontend/`](./frontend) | Next.js (TypeScript) client using Tailwind CSS and shadcn/ui |

---

## Getting Started

### Prerequisites

- JDK 25 (backend)
- Node.js 24 and npm (frontend)
- Docker, optional, for container builds and Docker Compose

### Development

Run each half in its own terminal.

**Backend**: recompiles automatically on code changes.

```bash
cd backend
./gradlew bootRun
```

Runs at http://localhost:8080

**Frontend**: hot reloading.

```bash
cd frontend
npm install
npm run dev
```

Runs at http://localhost:3000

### Docker

Each half has its own `Dockerfile` and `docker-compose.yml`.

```bash
# Backend (also starts a PostgreSQL database)
cd backend
docker compose up --build -d

# Frontend
cd frontend
docker compose up --build -d
```

Or build and run an image directly:

```bash
docker build -t backend ./backend && docker run -p 8080:8080 backend
docker build -t frontend ./frontend && docker run -p 3000:3000 frontend
```

### Profiles

The active Spring profile selects the database.

- **postgres**: connects to an external PostgreSQL instance
- **h2**: in-memory H2 database, no environment variables required

When running with the `postgres` profile, these must also be set:

| Variable          | Description                     |
| ----------------- | ------------------------------- |
| DATABASE_NAME     | Name of the PostgreSQL database |
| DATABASE_USER     | Username for the database       |
| DATABASE_PASSWORD | Password for the database user  |

### Configuring AI

AI feedback is built from three **use cases**. Each runs on its own **provider** and **model**, so they can be
mixed freely, for example screenshots analysed by a hosted model and text generated by a local one.

| Use case               | What it does                                            | Needs a vision model |
| ---------------------- | ------------------------------------------------------- | -------------------- |
| `image-analysis`       | Interprets drawing screenshots                          | Yes                  |
| `fact-generation`      | Writes the neutral fact note from a player's guesses    | No                   |
| `fact-framing-rewrite` | Rewrites the fact note in the player's assigned framing | No                   |

Every provider must speak the **OpenAI chat completions API**. OpenAI, Gemini, OpenRouter and Ollama all do, so no
extra dependency is needed to switch between them.

#### Quick start (OpenAI only)

Set an API key and a model for each use case. Everything else has a default.

| Variable                                        | Description                                        |
| ----------------------------------------------- | -------------------------------------------------- |
| OPENAI_API_KEY                                  | API key for the `openai` provider                  |
| FEEDBACK_AI_USE_CASE_IMAGE_ANALYSIS_MODEL       | Model that analyses drawings (must support images) |
| FEEDBACK_AI_USE_CASE_FACT_GENERATION_MODEL      | Model that generates fact notes                    |
| FEEDBACK_AI_USE_CASE_FACT_FRAMING_REWRITE_MODEL | Model that rewrites fact notes in a framing        |

Optional:

| Variable                                              | Default                     | Description                           |
| ----------------------------------------------------- | --------------------------- | ------------------------------------- |
| OPENAI_BASE_URL                                       | `https://api.openai.com/v1` | Point the `openai` provider elsewhere |
| FEEDBACK_AI_USE_CASE_IMAGE_ANALYSIS_TEMPERATURE       | `0.2`                       | Sampling temperature                  |
| FEEDBACK_AI_USE_CASE_FACT_GENERATION_TEMPERATURE      | `0.3`                       | Sampling temperature                  |
| FEEDBACK_AI_USE_CASE_FACT_FRAMING_REWRITE_TEMPERATURE | `0.4`                       | Sampling temperature                  |

#### Choosing a provider for a use case

Each use case picks a provider by name with a `..._PROVIDER` variable, defaulting to `openai`.

| Variable                                           | Default  |
| -------------------------------------------------- | -------- |
| FEEDBACK_AI_USE_CASE_IMAGE_ANALYSIS_PROVIDER       | `openai` |
| FEEDBACK_AI_USE_CASE_FACT_GENERATION_PROVIDER      | `openai` |
| FEEDBACK_AI_USE_CASE_FACT_FRAMING_REWRITE_PROVIDER | `openai` |

Built-in providers:

| Provider     | Base URL                                                     | API key variable                        |
| ------------ | ------------------------------------------------------------ | --------------------------------------- |
| `openai`     | `https://api.openai.com/v1` (or `OPENAI_BASE_URL`)           | OPENAI_API_KEY                          |
| `gemini`     | `https://generativelanguage.googleapis.com/v1beta/openai/`   | GEMINI_API_KEY                          |
| `openrouter` | `https://openrouter.ai/api/v1`                               | OPENROUTER_API_KEY                      |
| `local`      | `http://localhost:11434/v1` (Ollama, or `LOCAL_AI_BASE_URL`) | LOCAL_AI_API_KEY (defaults to `ollama`) |

Model names are whatever the provider expects: for example `vendor/model` on OpenRouter, or a tag such as `name:tag`
on Ollama.

**Example: screenshots on Gemini, text on a local Ollama model**

```bash
GEMINI_API_KEY=...
FEEDBACK_AI_USE_CASE_IMAGE_ANALYSIS_PROVIDER=gemini
FEEDBACK_AI_USE_CASE_IMAGE_ANALYSIS_MODEL=<a Gemini model that accepts images>

FEEDBACK_AI_USE_CASE_FACT_GENERATION_PROVIDER=local
FEEDBACK_AI_USE_CASE_FACT_GENERATION_MODEL=<an Ollama model tag>
FEEDBACK_AI_USE_CASE_FACT_FRAMING_REWRITE_PROVIDER=local
FEEDBACK_AI_USE_CASE_FACT_FRAMING_REWRITE_MODEL=<an Ollama model tag>
```

Only providers that a use case actually uses need credentials. Changing a provider or model needs a restart.

#### Adding or customising a provider

Providers live under `app.ai.providers` in `application.yaml`. Add an entry to introduce a new OpenAI-compatible
endpoint, then reference its name from a use case.

```yaml
app:
  ai:
    providers:
      my-provider:
        base-url: https://example.com/v1 # include the version path
        api-key: ${MY_PROVIDER_API_KEY:}
        timeout: 60s # per request, default 60s
        max-retries: 2 # default 2
        headers: # optional extra headers on every request
          X-Title: risktionary
```

| Setting       | Default                     | Description                                                      |
| ------------- | --------------------------- | ---------------------------------------------------------------- |
| `base-url`    | `https://api.openai.com/v1` | API base URL, **including its version path**                     |
| `api-key`     | none, required if used      | API key. Providers that need none still need a placeholder value |
| `timeout`     | `60s`                       | How long one request may take                                    |
| `max-retries` | `2`                         | How many times a failed request is retried                       |
| `headers`     | none                        | Extra headers sent with every request                            |

The application fails at startup, naming the use case, if a use case refers to a provider that is not configured or
has no API key.

#### Notes

- **Vision.** `image-analysis` sends screenshots, so its model must accept images.
- **Speed.** Before a round is saved the game waits for outstanding AI calls, up to
  `app.game.persistence.pending-ai-timeout` (default `10s`). Slow models may need this raised, with a matching
  provider `timeout`. Calls still running after the wait are abandoned and counted on the round.
- **Prompts.** The prompts in `backend/src/main/resources/ai/prompts` were tuned against OpenAI models. Smaller
  models follow rules such as "never reveal the answer" less reliably, so check the output after switching.
- **Token usage.** Usage is recorded for every AI call with its provider and model. Providers that report no token
  counts are recorded as zero.
- **Research data.** Each game records the provider, model and temperature of every use case
  (`risktionary_game_ai_use_case`) so results can be compared across models.
- **Tests.** No API keys or network access are needed; the test configuration replaces every model with a mock.

## Frontend

### Project structure

The codebase is feature-first: logic is organised by domain rather than technical layer, so everything for a feature
(components, hooks, types, API calls) lives together under `features/`.

```
frontend/src/
├── app/                  # Next.js routing
├── components/           # Shared UI primitives
├── features/             # Domain features
│   ├── auth/
│   └── game/
├── hooks/                # Shared React hooks used across multiple features
├── lib/                  # Framework-agnostic utilities (API, config, routes)
└── providers/            # React context providers
```

Each feature is self-contained:

```
features/<name>/
├── components/   # UI components scoped to this feature
├── hooks/        # React hooks scoped to this feature
├── stores/       # Zustand stores, slices, and selectors
├── socket/       # WebSocket subscription setup
└── types/        # TypeScript types scoped to this feature
```

### Environment variables

All optional. Defaults make local development work without setup.

| Variable            | Description                                    | Default                |
| ------------------- | ---------------------------------------------- | ---------------------- |
| NEXT_PUBLIC_API_URL | Base URL for the backend API                   | http://localhost:8080  |
| NEXT_PUBLIC_WS_URL  | WebSocket endpoint for real-time communication | ws://localhost:8080/ws |

These are prefixed with `NEXT_PUBLIC_`, so they are exposed to the browser and baked in at build time.

## CI/CD

A single GitHub Actions workflow (`.github/workflows/ci.yml`) runs on every push:

- **Backend**: runs tests, then builds the Docker image.
- **Frontend**: runs lint, then builds the Docker image.

Pushing a semver tag (e.g. `v1.2.3`) validates the tag and publishes both images to GHCR as
`risktionary-backend` and `risktionary-frontend`, tagged with the version and `latest`.

The frontend build reads `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_WS_URL` from repository variables.
Dependabot (`.github/dependabot.yml`) checks both projects, their Dockerfiles and the workflows weekly.
